═══ PART 1 — THE QUEUE-REPLAY FAULT: ROOT-CAUSED AND CLOSED ═══
(The P0 D4 open item "fresh NVComputeQueue [wait->exec(gx)->signal] wedges on the
first wait" is RESOLVED. It was never a queue-machinery bug.)

THE ANSWER — three stacked causes, all now laws:
  1. THE NAME LAW CONFIRMED AS THE HISTORICAL WEDGE (P0 law 1): the fault was
     only ever observed in MM_P0_d3_gather.py, whose programs were loaded as
     TinyELF(name="MM_P0_gx8e256nw32") = FILE PREFIX != cubin symbol. The
     per-kernel .nv.info/.text/.nv.shared sections then don't match ->
     prog_addr = whole-ELF base + shmem/stack unparsed -> degraded QMD ->
     SM Illegal Instruction -> the QMD never completes -> its release never
     fires -> the host timeline wait WEDGES -> device fault. The post-fix
     harness (d3_final) never re-ran the queue path, so the wedge stayed
     "unexplained" in the P0 record.
  2. THE SELF-DEADLOCK OFF-BY-ONE (found live, run-1 of MM_P1_q): capturing
     prev as `dev.timeline_value - 1` AFTER calling next_timeline() makes the
     graph WAIT ON ITS OWN SIGNAL VALUE (v both wait and signal) -> deadlock,
     identical wedge signature. LAW: capture prev BEFORE reserving v (the last
     SIGNALED value), exactly as gcycle's run_tokens does.
  3. THE PIPELINING LAW (T4, the real platform constraint): submitting a second
     graph train while the first is still executing FAULTS with
     SKEDCHECK22_INVALIDATE_ACTIVE_QMD — the P7F1 law, TIMING-DEPENDENT
     (T3's same-object depth-2 x4 survived by luck; T4's first pair faulted).
     THE PRODUCTION LAW: WAIT EVERY graph before the next submit (gcycle
     wait_each=True / PG_WAIT=1 semantics — which is what production decode
     and prefill actually run). No depth-2 pipelining of graph trains.

What is PROVEN CLEAN (T1/T2/T3, name-law-compliant programs):
  - Lone-submitted [memory_barrier -> wait(prev) -> exec -> signal(cur)] trains
    COMPLETE. The W2 "lone graphs never complete" law does NOT apply to this
    queue class — the eager path always completes because hcq_profile's
    timestamps consume the QMD release slots, pushing its signal to the
    NVM-semaphore + NON_STALL_INTERRUPT path; graph trains signal via the bare
    QMD release and complete fine too. The gcycle kicker remains harmless.
  - QMD-release signals, var-patched waits/signals, dedicated cpu_access
    kernargs slabs, VA pointer tables from device memory, chained
    dependent_qmd0 execs, and even same-object resubmission after a completed
    wait — all clean.

THE DELIVERABLES:
  - 256+256 replays [mm_eidmut -> gx] with device-mutated eids: eids EXACTLY
    match the numpy affine sim; det x2 OK (NaN-aware compare: the ys of random
    banks are ~22% NaN — plain np.array_equal FALSE-ALARMS on them; the proven
    compare is (a==b)|(isnan(a)&isnan(b)); finite-frac 0.78).
  - Router chain [hrot -> rt8e256poc -> gx704] x 256 in-graph: rt top-8 EXACT
    vs numpy on the drifted h; det x2 OK (h/eids/ys).
  - ENDURANCE: 1024 consecutive wait-each replays CLEAN (582 us/replay) — no
    ~950-cycle-class fault on this path (the budget concern remains for
    452-kernel production graphs at M1A_GEN_REBUILD_EVERY=256, unchanged).
  - THE GRAPH-PATH GB/s NUMBER P0 couldn't measure (wait-each, incl the
    ~0.3-0.6 ms host pacing per graph):
      [mut->gx] 88-pair: 670 us/cycle = 59 GB/s effective (submit-bound)
      [hrot->rt->gx] 704-pair (317 MB/cyc): 2.98 ms/cycle = 106 GB/s effective
      production chain [hrot->rt8e256->gx8e256up] 704-pair (634 MB/cyc):
        4.34 ms/cycle = 146 GB/s in-graph (kernel-only estimate ~156)
      K=8 decode shape (P=9 -> 72 pairs, 67.1 MB/cyc): 683 us/cycle = 98 GB/s
        effective (pacing-dominated at this small shape)
    In production the pacing is PER GRAPH (one train per token across all 40
