**THE ANSWERS:**
- **(a) GEMM per 64-pass = 124.7ms** (sum of the 6 GEMM classes). The P12-rate
  model (~110-125) WINS; the P7E7 SC classsync number (224.7ms/256tok = 56
  per 64-equiv) did NOT reproduce — it was inflated by the classsync method
  or the SC plan's launch pattern. In-graph m64/m32x2 ratios: fd 0.80, qg
  0.74 (standalone-eager was 0.60-0.69 — enqueue/graph effects compress it).
- **(b) Attention at 64 rows: NO structural amortization.** The grid-doubled
  t32 is ILLEGAL BY CONSTRUCTION — pf_attn32c.cu decodes `g = blockIdx.x /
  (NHP*S)` as the KV GROUP (kv + g*CTXK*256, only 4+4 exist) with ROWS=16
  hardcoded; doubling the grid reads OOB. So 4x t32 windows: 23.17+1.54 =
  24.7ms/64 vs 27.0 (2x per-32) = only **-8.5%** (queue-adjacency, not math).
- **(c) Norms: hh/n strongly sublinear** (0.93+0.23ms/64 vs ~3.2+0.8
  diet-equivalent — the row-per-CTA launch floor amortizes 3.4x); **ab flat**
  (13 CTAs/row already saturates); pre64 mildly negative (-0.4ms/64c).
- **WALL: M64 med 176.4ms/64tok = 361.1 tok/s vs M32 98.9ms/32 = 320.9
  (same boot; banked P12 319.1) = +12.5%.** Chunk = 725 launches (vs 541
  M32-diet); PG_SPLIT sweep: 2=186.9 / 3=185.0 / 4=184.2 (split4 -2.7ms but
  STATE-UNVERIFIED — see laws; ship stays split=2).
- **THE 400 QUESTION: M=64 alone does not cross it.** Full m64 coverage
  (adding fg/fu at ~0.74-0.80x) arithmetic: GEMM 124.7 -> ~112, chunk ~168,
  ~380 @2k-class. The remaining pools after that: qkv (m32x2, quarantined),
  attention (needs a ROWS=32/64 kernel = new numerics, Tier-2), scan (serial
  chain), and the P14 ffn serial-chain ceiling. **Next rung: M=128+WY (the
  chunked-scan numerics program) or the ffn smem ping-pong (P14's priced
  1.3-1.6x on the 53ms pool). Realistic endpoint unchanged: ~330-400 @100k.**

## 2. The tail seam — three stacked bugs (the 8k-gate failure postmortem)

The first 8k gate FAILED (F 6.7e-1, GATE A 0/60, the 22525 attractor) while
2k passed. Root causes (all in the r = N % 64 M32-tail delegation, none in
the M64 chunks themselves — N=7680 r=0 was bit-identical at every step):
1. **pos_slot starvation**: M64 chunks track position in pos_arr64/pos_w64
   and never write pos_slot — the tail read a STALE pos and re-ran at pos 0,
   clobbering kv rows 0..31. FIX: win_up pos_slot = pos0+64*nc before the
   tail. **LAW: every prefill path must leave pos_slot = the running pos.**
2. **Ambient-flag graph-cache keying**: _pf_graphs keyed on the module
   _M64ON flag — the 32-token tail (len < 64, M32 code path) replayed the
   STALE M64 GRAPH on ids64/pos_arr64 = deterministic garbage. FIX:
   m64_set(False) around the tail delegation. **LAW: the graph cache key
   must reflect the plan ACTUALLY submitted, not the ambient mode.**
3. **Head running post-tail**: the wall-time fix removed the tail's `return`,
   so the head re-ran on _pf_last64 row 7679 (stale) AFTER the tail's own
   correct head — logits/tok_slot-only corruption with a clean trunk. FIX:
   r>0 returns after the tail (the M32 tail does its own head/hlast/seed).
Also fixed: prefill_batch_m64 now returns the TOTAL wall (was returning the
tail's duration — the 8k gate's "0.3s prefill" artifact).
After the fixes: N=7712 (120 M64 + 1 M32 tail) BIT-IDENTICAL vs M32 all keys.

## 6. Laws + gotchas banked

1. **The running-pos law**: any prefill path that positions kernels via its
   own buffers (pos_arr64/pos_w64) MUST still write pos_slot before
   delegating tails — consumers (the M32 tail, the head, serve.py) read it.
2. **The graph-cache ambient-flag law** (see §2.2).
3. **PG_SPLIT=4 is STATE-UNVERIFIED** — timing measured (184.2 vs 186.9) but
   no bit-identity gate ran at split 4 before ship; ship = split 2. A split-4
   bit-gate is a cheap follow-up if the -2.7ms is wanted.
4. Grid-doubling the t32 attention is structurally illegal (g = KV group,
   ROWS=16 hardcoded in pf_attn32c.cu) — a 32/64-row attention needs a new
   kernel (Tier-2 numerics) or the A4-fused arm.
5. pfk_pre64 at NC=1 works (ywin=0, g=24) — the TROWS/window decode is
   clean; pre64 is ~30% slower per row than 2x pre32 (113 vs ~88us/64rows;
   24-CTA launch underfills) — PF_M64_PRE32=1 is the fallback if it matters.
6. `pr` (E.pr) is a plain dict but E.P's Bufs has NO __contains__/__setitem__
   — the `if n in pr` pattern in ensure_sc is LATENT-BROKEN (never runs with
   PF_SUPER=0); ensure64 uses a loaded-set guard.
7. The m64/m32x2 in-graph ratio (0.74-0.80) is materially worse than the
   standalone-eager ratio (0.53-0.69) — enqueue/graph effects compress the
   m64 win; standalone m64 bench numbers DO NOT transfer to in-graph.
8. sed-by-line-number on a concurrently-edited file bit silently (the
   E.P/E.pr binding bug) — pattern-based fixes only.

## 7. Next-stage recommendation (Stage 0's verdict, per the mission)

- **M=64 alone: shipped at +7.5-12.5%; the 400 cross does NOT happen on this
  rung.** Full packed7 m64 coverage (fg/fu) is worth only ~+6-7% more AND is
  VRAM-blocked both-live in the daemon (the decode G_CYCLE graphs pin the
  originals — the P7F3 law; free-then-upload is illegal in the serving
  process). Do NOT chase it.
- **The remaining @2k pools after M64**: ffn 53.2 (P14's smem ping-pong
  price 1.3-1.6x on this pool = the biggest single lever, ~-16-20ms/chunk),
  qkv 8.2 + oa 4.6 (small), attention 24.7 (needs new-row kernels), scan
  27.6 (serial). **Recommended P16: the P14-priced ffn smem ping-pong (87KB
  <= 100KB config) — it composes with M64 (the m64 ffn twin once fg/fu
  coverage exists, or the classic x2 today) and alone projects ~380-400 @2k.**
- M=128+WY remains the structural rung (chunk seams halve again; the WY
  numerics program is the cost) — price it AFTER the ffn lever.
- Realistic endpoint unchanged: ~330-400 @100k (50-60% of 662).
